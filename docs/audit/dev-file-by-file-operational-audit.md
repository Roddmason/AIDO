## Criterio operativo

- AIDO debe converger a una GUI tipo Codex con threads, loops, agentes, runtimes reales, Git/gitleaks real, plugins y skills.
- No se acepta éxito productivo simulado: sin mocks productivos, botones sin backend real, chat que solo persiste prompt ni pipelines `queued` decorativos.
- Ejecución real significa ToolBroker + policy + workspace + evidence; si no se puede ejecutar, la UI/API debe exponer `blocked` o `configuration_required` con razón técnica.
- La clasificación `delete` se reserva para archivos sin importadores, referencias textuales, tests, OpenAPI, docs ni scripts. En este baseline no recomiendo borrado directo: hay referencias activas o deuda de transición que requiere reemplazo previo.

## Hallazgos críticos

- `local_control_center/threads/**` y `local-control-center/web/src/features/shell/**` son el eje correcto para la experiencia tipo Codex; deben pasar a ser el flujo primario.
- `sessions_chats`, `pipelines` y `WorkbenchPage` siguen activos por imports, OpenAPI, tests y overview. No deben borrarse todavía, pero sí migrarse: hoy son deuda de transición porque mantienen el modelo session/chat/pipeline junto al nuevo modelo thread/message/event.
- `Home`, `Workbench`, `Workflows`, `Review`, `Audit`, `Assessment` siguen navegables. El objetivo de producto exige simplificar la elección visible del usuario a Consulta o Agentes/Loop; esas superficies deben quedar como soporte, inspector, settings o archivo, no como caminos paralelos de ejecución.
- Los scripts y manifests ya contienen barras de calidad relevantes (`quality`, `security:secrets`, gitleaks, OpenAPI, runtime smoke). Mantenerlos como criterio de release; no sustituirlos por estados visuales.
- La documentación contiene planes/auditorías históricas útiles como evidencia, pero debe separarse de docs canónicas para evitar que contradiga el estado operativo actual.
